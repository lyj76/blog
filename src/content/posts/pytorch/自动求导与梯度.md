# PyTorch 自动求导与梯度：计算图 / backward / 梯度管理

训练时为什么每步都要 `optimizer.zero_grad()`？为什么 `loss.backward()` 之后 `.grad` 才有值？这篇把自动求导的内部机制讲透。

## 1. 计算图与叶子结点

自动求导的核心是把「运算历史」记成一张**计算图**：每次张量运算都会产生一个新张量，并用 `grad_fn` 记录"我是由哪个运算算出来的"。链式法则就沿着这张图反向传播：

```python title="leaf-example.py"
import torch

A = torch.tensor([3.0], requires_grad=True)   # 用户直接创建 → 叶子
W = 2 * A                                     # 运算产生 → 非叶子
L = W ** 2                                    # 再往后一层

print(A.is_leaf, W.is_leaf)   # True False
print(W.grad_fn)              # <MulBackward0> —— 指向"谁生成了我"
```

- **叶子结点（leaf）**：用户直接创建、不依赖其他张量的张量（如 `A`、模型参数）。`requires_grad=True` 时，它是**梯度更新的最终落点**
- **非叶子结点**：由运算产生（如 `W`、`L`），有 `grad_fn` 指向产生它的运算，默认不保留 `.grad`
- **`requires_grad` 是开关**：`True` 才被记进计算图、才会在 backward 时收到梯度——模型参数默认 `True`，普通张量默认 `False`
- `detach()` 会产生一个新叶子，切断与原计算图的联系

## 2. backward()：沿计算图反向传播

`backward()` 从调用它的张量出发，沿**计算图反向**走一遍，用链式法则把梯度累加到每个叶子结点的 `.grad`：

```python title="backward-example.py"
import torch

A = torch.tensor([3.0], requires_grad=True)   # 叶子结点
W = 2 * A                                     # 非叶子，grad_fn=MulBackward
L = W ** 2                                    # 标量损失

L.backward()                                  # 反向传播
print(A.grad)   # tensor([24.])
print(W.grad)   # None —— 非叶子默认不保留
```

- `backward()` 必须从**标量**张量调用（多元素张量需传 `gradient` 参数）
- 反向走完后，所有 `requires_grad=True` 的叶子结点 `.grad` 被填充
- 非叶子结点（如 `W`）默认 `.grad = None`，因为中间梯度用完就丢，省内存

## 3. 谁可以调 backward：不只有 loss

任何「背着计算图（有 `grad_fn`）的标量张量」都能发起反向——`loss` 只是最常用的那个（它恰好是前向的终点）：

```python title="who-can-backward.py"
W = 2 * A
W.backward()        # 非 loss 也能反向 → dW/dA = 2
print(A.grad)       # tensor([2.])
```

- **叶子结点（参数）是梯度落点，不是发起者**：在叶子张量上直接 `.backward()` 没有计算图可走（实测 torch 2.4.1 不报错，只是把 `.grad` 置 1，对训练无意义）
- 只要满足「有 `grad_fn` + 标量」两个条件，任何张量都能发起反向——「只有 loss 能 backward」是误解

## 4. .grad 是累加器：梯度为什么会累积

`.grad` 是**累加器**，不是赋值器：

```python title="grad-accumulate.py"
A = torch.tensor([3.0], requires_grad=True)
L = (A ** 2).sum()

L.backward()
print(A.grad)   # tensor([6.])   第一次

L.backward()
print(A.grad)   # tensor([12.])  第二次 —— 累加！不是覆盖
```

- 每次 `backward()` 都把新算出的梯度**加到** `.grad` 上，不清零
- 设计原因：方便实现梯度累加（gradient accumulation），小显存模拟大 batch
- 副作用：训练循环里不主动清零，梯度会越累越大，参数更新方向完全错乱

## 5. zero_grad()：为什么每步必须清零

上一节讲了 `.grad` 是累加器。所以每个训练 step 都要先清空梯度，否则新旧梯度累加、更新方向就错了：

```python title="zero-grad.py"
optimizer.zero_grad()   # 清空所有参数的 .grad（等价写法：param.grad = None）
```

- **机制**：`zero_grad()` 遍历优化器里的所有参数，把 `.grad` 置为 `None`（`set_to_none=True` 是默认，比原地清零更省显存）
- **为什么是 None 而不是 0**：`.grad` 置 `None` 后 PyTorch 能复用这块显存，等下一次 `backward()` 时才重新分配
- **完整训练姿势**：`zero_grad → backward → step` 三步的顺序与原因见「训练循环与优化器」篇——这篇只管"为什么要清零"

::::warning
**`zero_grad()` 不是可选步骤**：漏掉它，`backward()` 算出的梯度会和历史梯度累加，参数更新方向完全错乱。
::::

## 6. retain_grad()：查看中间梯度

非叶子结点默认不保留 `.grad`，调试时想看就显式调用：

```python title="retain-grad-example.py"
A = torch.tensor([3.0], requires_grad=True)
W = 2 * A
W.retain_grad()        # 显式要求保留 W.grad
L = W ** 2

L.backward()
print(W.grad)   # tensor([12.]) —— 现在能看到了
```

- `retain_grad()` 必须在 `backward()` **之前**调用
- 只用于调试，正式训练别开（多存一份中间梯度，显存翻倍）
- 链式法则验证：`dL/dW = 2W = 4A = 12`，`dW/dA = 2`，`dL/dA = 12 * 2 = 24` ✓

## 7. with torch.no_grad()：推理上下文

```python title="no-grad-example.py"
model.eval()
with torch.no_grad():
    logits = model(input_ids)   # 前向，但不建计算图
# logits.grad_fn is None —— 不追踪梯度
```

- `no_grad()` 上下文里所有运算**不记录到计算图**，`grad_fn` 为 `None`
- 推理/评估时必用：省显存、加速、避免误调用 `backward()`
- 等价写法：`@torch.no_grad()` 装饰器

::::tip
**`model.eval()` 与 `no_grad()` 是两件事**：`eval()` 切换模块的 `training` 标志（影响 Dropout / BatchNorm 行为）；`no_grad()` 关闭计算图追踪。推理时**两个都要**：`eval()` 改行为，`no_grad()` 省显存。
::::

## 小结

| 语法 | 作用 / 返回 |
| --- | --- |
| `A.is_leaf` / `A.grad_fn` | 是否叶子结点 / 谁生成了我（计算图结构） |
| `L.backward()` | 沿计算图反向，把梯度累加到叶子 `.grad` |
| 谁可以发起 backward | 任何有 `grad_fn` 的标量张量（loss 只是最常用的；叶子是梯度落点） |
| `.grad` 累加 | 每次 backward 累加不清零（梯度累积的底层机制） |
| `optimizer.zero_grad()` | 清空所有参数 `.grad`（`set_to_none`，防累加） |
| `W.retain_grad()` | 让非叶子 `W` 也保留 `.grad`（调试用） |
| `with torch.no_grad():` | 关闭计算图追踪（推理用） |
